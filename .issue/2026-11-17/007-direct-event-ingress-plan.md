# 007 — 两种事件接入方向

## 目标与约定
用户确认：外部直接向 Newbot 投递事件，或 Newbot 通过插件连接外部服务。不要求安装中继插件，不把具体业务写进平台。
实际：当前触发器只接受插件订阅，插件 Webhook 也要求 NEWBOT_EVENT_RELAY_*；relay-events 还将中继包装成另一事件源。预期：Newbot 自带经认证的通用 CloudEvents 接收端；业务插件主动连接外部；插件 Webhook 回调直接落到 Newbot。
不变量：一个来源+事件 ID 在同一触发器只产生一次执行；任务停用/删除/配置改变后不能继续接受旧授权；持久化确认后重启不丢；事件入口不能取得管理 API 权限；任务执行沿用固定会话。

## 证据及根因
有代码证据：examples/relay-events/server.ts 的 subscribe/lease/ack 包装和 delivery=poll；server/event-subscriptions/webhook.ts 将回调固定拼到公网中继；service.ts 仅在 relay 配置齐备时启用 webhook。独立连接插件已有 poll/push，不需要改成平台业务实现。
产品改进：新增通用“接收事件”，不是恢复已删除的业务专用 Webhook 类型或旧格式兼容。

## 同类风险
- 有代码证据：共享订阅 validate/refresh/status 假定全部事件都有账号；增加直接接收后必须按来源分流。
- 有代码证据：统一登录/Origin 校验会拒绝外部投递；仅具体投递路由改用独立凭证，管理路由继续登录验证。
- 有代码证据：receiveEvent 已有事务去重、配置版本检查、固定会话队列；直接接入复用，不另造执行器。
- 待验证：无效凭证、重复/冲突事件、重启、暂停/删除/编辑、凭证重置。
- 待验证：插件 Webhook 的签名、验证挑战、订阅取消、重启恢复改为直达后保持成立。
- 待验证：移动端接收地址/凭证弹层溢出、关闭再开与迟到响应；现有插件选择不受影响。

## 范围与实施
1. 通用直收触发器 schema、带独立凭证的 CloudEvents HTTP 入口与管理配置；复用任务队列与去重。
2. 插件 Webhook 回调改成本机持久化接收，不再依赖平台 relay 配置；原有插件主动连接不变。
3. 自动任务添加“接收事件”，保存后获取地址/凭证；沿用 Picker/现有样式。凭证不进入任务提示词与事件上下文。
4. 测试、浏览器验收、文档和自动边界检查。
不做：引入 MQTT 基础设施、业务供应商专属解析、任意服务原生兼容声明；不在未替换真实链路前停止现网中继。独立 relay 服务可作为外部工具保留，但平台不强制依赖。无旧格式兼容，新协议不猜测缺失数据。

## 验收
直收：无插件账号即可创建；认证投递触发一次；重复返回原 run；冲突拒绝；重启仍去重；停用/删除拒绝；重置旧凭证失效；两次独立事件复用同一会话。
插件：poll/push 回归；Webhook 在无 relay 配置时直接验证并接收，签名失败拒绝，取消后不再接收。
浏览器：390/1280 宽度，入口选择、保存、凭证显示/复制、关闭和滚动，无布局漂移。
