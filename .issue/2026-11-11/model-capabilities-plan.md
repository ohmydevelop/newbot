# 模型用途、能力登记与原生热切换闭环

## 目标、现象和不变量
MC-01：普通网关目录仅有 ID，Bridge 丢弃可选元数据，内核使用 Synthetic 兜底而拒绝任务内切换。MC-02：目录中嵌入、重排等模型直接进入聊天选择器。MC-03：已有跨网关补丁解析目标模型时仍借用会话初始模型管理器，同名/自定义模型可能选错元数据。均有源码证据：providers.probe、session-runtime.catalog、step_activation、step_settings。用户明确授权继续修复包括 Codex 内核。

不变量：目录发现不等于能力确认；聊天用途、协议兼容、上下文容量分别判断；网关/模型/配置绑定能力记录，不跨接收方借用；同一线程与任务继续，下一尚未开始的请求才变更；不重放工具；当前审批、Guardian、历史类型和容量检查保留；SQLite 为配置事实来源，不改个人 Codex。

## 调查与关联范围
- 官方网关规范确认 ID 列表不足，Codex 完整 catalog 可提供上下文/推理/工具信息：https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway 。已读取本地 fe2f185 与现有补丁；不再次无关升级内核。
- MC-02 用途优先读取明确任务/输入输出类型；无类型时只对明确非聊天标识及常见向量系列作保守排除。未知不得宣称兼容；原始目录在管理流程仍可诊断。历史/手填/默认值不能把已确认非聊天模型加回选择器或绕过服务端。
- MC-01：完整可信 catalog 优先保留；无 catalog 时以两个隔离 Responses 请求验证流式、受控 function 调用、工具结果回传，不执行 shell/MCP/业务动作。失败不写“已验证”；不探测不相关模型。保存可观察能力与验证范围，不编造厂商最大上下文或推理档位。
- MC-03：目标原生元数据以明确目标路由快照提供并严格解码；旧当前 Synthetic 模型只在可信、匹配的能力确认及原有权限约束不变时迁移，不直接删除 Synthetic 拒绝。目标容量/模态/不可移交压缩历史等约束仍需通过。
- 生命周期：目录缓存、配置/接收方修改失效、当前任务/下一轮、连续切换、失败回滚、取消、SQLite 重启均纳入。其他插件、RAG、模型网关转换实现不纳入。
- 用户目录新增/删除文件与上一轮未提交修改保持原样。

## 阶段与验收
S0 调查与计划：完成本记录；保存运行、源码、文档证据。
S1 模型用途与完整目录：统一解析、过滤与服务端验证；覆盖 metadata/non-chat 名称、同名、手工模型、默认/历史回填；独立测试。
S2 能力确认与持久化：绑定端点配置的能力记录、有限上下文验证、受控 native catalog；按需验证并反馈，失败保持选择与草稿；不把默认参数当成最大能力。只写隔离资源文件，不写 config.toml。
S3 原生补丁与类型：独立补丁集，隔离源码/构建，按路由解析 metadata；保留全部权限与历史校验；真实 App Server 两个自定义模型跨网关继续同一任务，工具只一次，旧当前 Synthetic 的安全补全单独验证。
S4 联调与发布：类型、构建、关联自动测试、真实浏览器选择器排除及验证过程；空闲维护锁后更新开发服务，核对个人配置/持久数据与公网一致。原生 build 未完成或证据不足不得标完成。

无完整模型调用框架；不适配特定厂商私有业务。主动兼容性验证可能消耗少量模型额度；只请求选择的模型、使用合成内容，不发送会话历史/秘密做探针。模拟接收方不等于实际商业 Provider 验证。计划完成状态和证据持续写 `model-capabilities-progress.md` 与 `evidence-model-capabilities/`。
