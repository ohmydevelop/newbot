# 应用信息层级与网关工具格式：调查结论

## AP-01 / AP-02：展示责任与命名来源

宿主承担隔离、能力限制和审批，用户此时要读的是业务内容。原实现把宿主诊断直接常驻在业务区：协议名、内部连接器哈希、原始工具标识、完整能力清单。关联入口包括 App 操作授权、原生工具授权和普通信息表单；这些地方同样用协议名代替任务语言。此类问题有截图和 JSX 证据。

另外，聊天工具行只从 `settings.mcp` 取标题。插件组件按先前需求从独立连接器目录移除后，工具行失去了标题来源，回退到内部标识。这是目录用途与展示数据来源混用，不能通过把插件工具重新塞回独立连接器列表修复。

实现：从原生线程目录提取 `title` / `annotations.title`；只存有界、非敏感的名称映射，按线程隔离，供流式事件、历史、App 及审批使用。原始执行标识、权限目录、授权参数都不改变。接收方名称取已配置连接器或包内声明，未知操作仍用真实工具名，不推测含义。生成的插件连接器哈希在主阅读区以中性名称兜底，原标识留在授权详情。

App 只保留紧凑标题、关闭、必要加载和恢复状态；授权时展示接收方、具体操作和可展开参数。普通输入的隐私提示保留。A2UI 的敏感输入提示、配置中的环境变量/请求头字段、存储清理后果与文件完整性失败均有决策价值，本轮不删除或泛化隐藏。

## PT-01 / PT-02：不能把模型自述当成底层诊断

实际会话的模型确为 `minimax-m3.1-flash`。仅记录事件类型与调用名称的 `rollout-classification.json` 显示警告出现于模型生成的条目/回答及其镜像事件，未取得网关原始响应或转换日志。这足以确认用户遭遇的现象，但不足以证明网关具体实现，也不能断言模型本身不支持 MCP。

独立运行目录中的 Codex 0.165.0 + 模拟 Responses/MCP 探针完成 7 组检查（`native-tool-shapes.json`）：

| 场景 | 实际发布与结果 |
|---|---|
| minimax 默认 | MCP 工具在 `mcp__shape` namespace 中；规范回包后实际执行成功 |
| `non_prefixed_mcp_tool_names=true` | 只去掉 namespace 名称前缀，没有变成扁平函数；调用成功 |
| `incremental_tools=false` | MCP 仍在 namespace；调用成功 |
| `code_mode_host=false` | MCP 仍在 namespace；调用成功 |
| 模拟转换器丢弃 namespace | 原生请求包含工具，但转换后不可调用；工具执行次数为 0 |
| deepseek 对照 | 同样发布 MCP namespace；规范回包后执行成功 |
| gpt-6-sol 对照 | 发布 code-mode 入口，通过原生执行桥调用同一 MCP 成功 |

共 6 次模拟 MCP 调用，0 次真实模型/业务调用。探针中的模型名称控制原生配置选择，响应由模拟器生成，因此这些结果不证明外部模型质量或服务兼容性。首轮探针使用 `never` 时受原生工具审批拦截；调整为仅测试连接器的显式模拟批准后完成验证，该夹具修正不改变产品策略。

结论：已证明 Codex 会发布工具，且三项候选开关不能将 MCP 改为普通函数。没有依据向产品下发所谓兼容参数。用户已确认网关是**外部服务**；其转换器需要完整保留 namespace 下的工具与返回路由，或供应方提供支持这些格式的模型路由。newbot 本轮不增加转换网关、不篡改插件、不自动换模型、不绕过 MCP 执行业务。
