# CHATGPT-RESTART-20261113：newbot 与 ChatGPT 重启关联调查

日期：2026-11-13，所有面向用户的时间为 Asia/Shanghai。
范围：用户询问原因与关联，本轮只读调查并保存记录，不实施产品或系统配置修改。

## 反馈、目标与约定

原始反馈：当前newbot所运行的codex是否会影响chatgpt，现在的chatgpt总是重启

- 用户目标：newbot 与 ChatGPT 可以同时稳定使用，确认重复退出是否由 newbot 引起。
- 触发条件：用户未提供具体操作及发生时间；本机系统日志能够定位两次桌面应用终止。
- 实际行为：2026-11-12 10:49:19 与 2026-11-13 11:49:15，ChatGPT 对应的应用 cgroup 被 systemd-oomd 终止；今天 11:54:35 应用再次启动。
- 预期行为：newbot 的启动、退出、配置写入只作用于自身实例；正常并行工作不应使桌面应用被系统终止。
- 不变量 I1：配置、认证、SQLite、工具管道与进程生命周期不得跨客户端串用。
- 不变量 I2：并行开发与服务运行需要在整机资源容量内进行，避免内存及交换空间耗尽。
- 区分：已确认的是系统强制终止与随后启动，不据此声称应用自身进行了自动重启，也不声称所有历史“重启”均由同一原因引起。

## 调查结论与证据

1. **已确认的直接终止原因：整机资源压力触发 systemd-oomd。**
   `evidence-chatgpt-restart/oomd.log` 记录今天 11:49:15 内存使用 7,382,528,000 / 8,158,904,320 字节，swap 使用 10,958,057,472 / 12,173,082,624 字节，均超过 90%。被选中的组为 `app-org.chromium.Chromium-307597.scope`。
2. **该组对应 ChatGPT，而非仅凭 Chromium 名字猜测。**
   桌面日志文件包含主 PID 307597，启动时间为今天 10:43:57，最后事件为 11:49:06；系统 scope 同时开始、在 11:49:15 以 `oom-kill` 结束。新主进程 PID 737327 在 11:54:35 启动，当前可执行文件为 `/usr/lib/chatgpt/ChatGPT`。
3. **同类现象已在其他入口发生。**
   昨天 PID 19719 对应桌面日志与应用 scope 在 10:49:19 终止；今天 code-server 在 10:58:46、11:23:02 被同一机制终止。它们支持“整机压力”判断，不支持把所有占用归因于某一个程序。
4. **当前 newbot 的直接客户端边界隔离成立。**
   实际二进制为仓库 `.data/native/releases/fe2f185-capabilities/codex`；实际 HOME、CODEX_HOME、CODEX_SQLITE_HOME、XDG 均在仓库 `.data/codex` 下。桌面应用使用 `/usr/lib/chatgpt/resources/codex`、个人 HOME 与独立应用目录。两者进程组与 cgroup 不同。newbot 实际环境未包含桌面工具管道及继承认证变量（只记录变量是否存在，不采集秘密）。
5. **源码、构建产物、运行入口已交叉核对。**
   服务从本仓库 `dist/server/index.js` 运行，监听 127.0.0.1:3100；`/api/ready` 返回 ready。当前入口导入 `chunk-DUG4CTAJ.js`，该实际公共构建块包含运行目录隔离、宿主环境过滤与定向停止逻辑。
6. **仍未确认。**
   缺少 OOM 时刻的逐进程内存历史，不能断言 newbot 是主要耗内存者、存在内存泄漏，或是每次退出的唯一诱因。当前快照只说明采样当时的状态。未收到用户对“整个桌面退出 / 网页刷新 / Codex 重连”的细分反馈。

官方架构参考：[OpenAI Docs：App Server](https://learn.chatgpt.com/docs/app-server)。具体故障结论依赖本机日志及运行证据，不能由一般产品文档替代。

## 后续处理计划（尚未实施）

1. 先在实际工作负载下采样整机 memory/swap、应用 cgroup 和 newbot 服务/任务子树，记录开始、繁忙与结束后的回落；将新退出时间与 journal 对齐。需要保留足够故障前数据，不能用退出后瞬时快照倒推。
2. 若确认开发任务并发造成峰值，优先降低构建/测试/代理任务并发并处理经确认可释放的空闲任务。用户当前只要求原因分析，不主动终止其现有工作。
3. 若需长期服务隔离，在取得实施范围后，为 newbot 及相关执行任务设计独立 systemd 单元和合理资源预算。目录隔离不等于内存限制；限额需要根据实测设置，并验证失败恢复，不能简单禁止 OOM 保护。
4. 若低负载下仍有退出，再按新发生时间调查桌面应用/renderer 的独立故障。

明确不处理：本轮不改产品代码、不升级桌面程序、不删数据/缓存、不清理用户任务、不改 swap、OOM 策略或桌面配置。与本问题无关的 UI 工作保持原样。

依赖与兼容：后续资源调整依赖工作负载测量及实施范围；不需要迁移 Codex 或会话数据库，须保留现有独立目录、登录状态和运行中任务。

## 第二轮核实：17:23–17:29 的自动重启

反馈补充：用户确认“没有明显操作也会重启”。目标与资源容量不变量沿用上文；本轮仍为只读原因调查，没有实施系统或产品改动。

已确认因果链：整机内存与 swap 同时超过 systemd-oomd 的 90% 阈值 → ChatGPT 服务组被 SIGKILL → 已安装的 Restart=always / RestartSec=10 自动恢复。17:23:25、17:25:07、17:29:16 三次终止各在十秒后恢复。实际服务、监督器源文件与 journal 已核对，自动恢复不等于内存原因已修复。

同类风险更新：ChatGPT 服务退出为“已复现（自然事件日志）”；code-server 17:15:41 同样被 oomd 终止，为“已复现”，共同机制为整机 RAM/swap 阈值。具体负载占用归属仍“待验证”，当前 RSS 快照不足以确定故障时最大贡献者。Wayland/GPU 日志有报错，但本轮三次进程退出有明确 oomd 原因，不将其列为已确认重启根因。ChatGPT 服务 MemoryHigh/MemoryMax 均为 infinity，未发现该服务自身硬限额。

后续顺序仍为故障前资源采样、识别可收敛负载、实施经授权的并发/容量方案，再验证 ChatGPT 与 code-server 在相同工作负载下不被终止；不以关闭恢复或 OOM 保护作为根因修复。不迁移账号及会话数据。

状态：本轮原因确认完成；资源治理未实施，故障未修复。证据见 evidence-chatgpt-restart-round2/ 和同目录进度记录。
