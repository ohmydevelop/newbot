# GCF-8 · 深层插件操作、Codex 多商店与附件消息

## 用户目标和触发
插件列表进入新建、导入、安装预览、编辑连接器、技能说明时，应延续 Grok 的层级、表单、按钮与颜色，减少技术说明。底层以 Codex 原生插件为主，多商店可独立添加、浏览、更新和管理。Claude/Grok 后续经明确转换器接入，不把不兼容的权限/钩子静默抹掉。发送附图消息后，正文气泡在前，图片独立在后，同一次消息连续展示。

## 不变量、证据及原因
1. GCF-7只统一目录容器，SkillImport仍有旧来源按钮组/密集技术摘要，ConnectorEditor继承旧表单样式；深层视觉不应另起一套。Grok当前实际表单是同面板面包屑返回、单列字段、低对比底色与右侧取消/主操作。当前Grok已出现新的设置导航版本，以实测深层表单为证据，不全盘替换已确认主目录。
2. 原生 generated/codex 有 marketplace/add/remove/upgrade；newbot仅有 imports:marketplace 单一根。Codex.discoveryMarketplaces循环每次写同一个newbot-imports键，多来源会互相覆盖。注册商店不是安装插件，安装身份应为name@marketplace，两个商店同名插件不能合并。
3. Message.tsx把所有content放在同一个背景div；App.tsx乐观消息又单独绘制正文和附件名。两入口必须共用正文/媒体布局，否则发送与服务端回执之间跳变。只调整呈现，不改历史数据或执行输入。
4. 官方依据：developers.openai.com/plugins/build/plugins（已打开并核对原生商店格式和命令）；code.claude.com/docs/en/plugin-marketplaces；docs.x.ai/grok/connectors。Grok是MCP连接器契约，不能声称存在已确认的通用插件包导入格式。

## 实施顺序与兼容
1. 完成深层参考和原生多商店调研，记录转换矩阵。
2. 商店管理使用Codex原生marketplace/add在独立目录准备快照；SQLite注册多个来源，验证来源/身份、版本和幂等操作，原有newbot-imports保持兼容。发现与运行配置传递完整商店映射。
3. 深层界面统一窄表单、标题/返回、来源选择、步骤预览、底部操作和短文案；管理商店作为插件中心按需入口，主目录提供商店筛选。新增技能书写入口与现有安全导入管线复用，不直接绕过SKILL.md验证。
4. 共用用户消息组件，文字、图片、文件分块；覆盖乐观发送及已有历史。
5. 自动化针对性验证、真实浏览器深层完整流程、独立视觉复核；备份/空闲维护锁后部署实际3100和原Cloudflare入口，核对配置/历史与真实模型。

不处理：更改Grok账号、使用未提供的第三方凭证、静默安装外部插件、全盘重构模型协议或照搬无法提供的托管能力。当前实际GitHub/hids错误保持真实状态，不隐藏。保留现有数据结构、插件安装根快照、私密字段保护与revision恢复机制；新增注册数据兼容缺省。

## 可观察验收
- 添加/取消/错误/导入预览/安装结果/编辑/返回都在同一视觉体系，手机390/320不溢出，桌面1440与浅深色检查。
- 至少两个独立Codex商店可注册并重启恢复；同名插件身份隔离；坏来源不覆盖旧状态，重复提交不重复注册；更新失败旧来源可用；有安装项的商店不可直接移除。
- 原生fixture实际解析和安装一个本地技能插件，区分模拟UI与真实Codex结果。
- 正文与图片独立容器，顺序稳定、纯图无空气泡，多图逐项可预览，乐观及回执无重复消息。
- 原访问地址得到新构建；用户配置和历史完整；真实模型短消息可完成。

### 验收发现补充（实施前）
纯附件被App发送保护、HTTP run schema和bridge turn schema共同要求非空text挡住，故无法走本计划的纯图验收。将约束统一为“正文或附件至少一项”，仍验证附件所有权/UUID/数量；空消息仍拒绝。空正文不生成虚假文字输入，首次标题使用“附件消息”。纳入HTTP行为测试和浏览器多图测试。另原生CLI配置路径不解析引号键，应传完整TOML market表；实际重启测试已经复现并用于验证修复。

共享操作边界补充：商店移除与插件安装必须互斥；否则移除检查与异步安装之间存在窗口。插件变更和商店变更共用registry锁，移除同时检查持久化安装状态，不能以一次发现失败当作“没有已安装项”。
