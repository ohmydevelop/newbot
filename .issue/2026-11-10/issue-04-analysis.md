# Issue 04：调查结论

日期：2026-11-10。范围：阅读分析 [04.md](04.md) 及其引用的 image-20、21、22、23、25.png。原文和截图不修改。本轮只做调查、隔离复现和规划，没有实施产品修复。

## 结论与证据基线

这不是一组单纯的样式问题。共同缺口有四个：等待状态没有统一来源；运行配置没有区分用户意图与本轮快照；模型能力缺少“未知”状态；共享控件和滚动容器没有统一约定。

- 当前运行 Codex 0.165.0；测试服务 PID 817676。工作树有大量既有未提交修改，不能以 Git HEAD 代表运行版本。
- 本地服务、公网主入口及磁盘前端均返回 `/assets/index-B-cWmD3y.js`，SHA-256 一致。MCP Apps 独立入口拒绝访问主页面。详见 [runtime.json](evidence-issue-04/runtime.json)。关键源码判断同时用实际构建的浏览器行为交叉核实，本轮未重新构建或重启服务。
- 浏览器调查使用现有 `dist/web`、临时数据库、IssueCodex 模拟运行时和本地模型目录，不调用真实 Provider，不使用真实凭证。结果见 [ui.json](evidence-issue-04/ui.json)，可重复脚本见 [inspect-ui.mjs](evidence-issue-04/inspect-ui.mjs)。它证明本项目的显示、布局和控制接口行为，不证明第三方模型兼容性。
- 已逐张查看本轮复现截图。页面未出现 JavaScript 错误。临时服务和浏览器已关闭。

### I04-01：等待状态存在，但信息不完整

数据路径是 `Codex.receive → approval → threadActivity.approval → newbot.activity → ThreadStatus`。`requestApproval`、`requestUserInput`、MCP elicitation 已被原生请求入口统一接收，但活动摘要只保存 `waiting`，没有等待原因、数量和目标。`ThreadStatus` 将其渲染为时钟及悬停文字“等待处理”，正文 `ChatTurn` 则只检查 `turn.status === inProgress`。

隔离复现同时观测到：侧栏 `aria-label=等待处理`、正文“正在处理 0 秒”、审批卡片可见。见 [waiting-light.png](evidence-issue-04/waiting-light.png)。因此不是没有审批功能，而是摘要和正文没有表达同一个阻塞状态。

更实质的同类缺口：A2UI `waitForAction` 在 `server/a2ui.ts` 中保存了自己的 waiting/pending，`server/index.ts:327` 的 tool 路由及 `server/bridge.ts:109` 的表单更新回调均未接入活动等待集合。它可能一直显示运行中。该项有代码证据，尚未做独立浏览器复现。

建议：统一按 threadId、turnId、请求来源和请求 ID 聚合“待用户处理项”，增加原因、数量、目标，不包含表单内容或私密值。侧栏显示简短可辨认的“需要批准”/“需要输入”，正文使用同一摘要，提供定位到待处理卡片的入口。多个请求中处理一个，不能提前显示恢复运行；过期、取消、断线和重启都必须重新核对。

等待是一种任务状态，不等于操作危险。普通等待可以用蓝色语义，高风险权限仍用警示色。状态位预留宽度，避免新增标签再引入列表跳动。当前凭证管理为独立操作，未绑定 threadId，不能把其等待状态无差别贴到所有聊天。只显示应用的 MCP iframe 也不自动算作等待。

### I04-02：能力未知被错误折叠为不支持

`server/session-runtime.ts:126` 只按模型 ID 从原生目录查 `supportedReasoningEfforts`，查不到就返回空数组；`:233` 的校验把空数组直接解释为“不支持”。浏览器给模拟目录中的未知模型提交 `low`，得到 HTTP 400“模型不支持该推理强度”。这个错误只证明本地校验拒绝，并不能证明模型不支持。

另外，同一模型 ID 跨网关直接复用原生元数据，也不能证明两个网关的实现完全相同。模型列表发现成功、参数传到了上游、上游实际执行了该参数是三个不同事实。

建议统一推理档位的中文名称、顺序和选择方式，同时增加按“网关＋模型＋配置版本”区分的能力状态：已知支持、已知不支持、未知。未知模型不再假装已经证实“不支持”。用户主动选择的未知档位可进入待验证流程；真正不支持的档位给出原因。不能把低/中/高任意映射为未经验证的 token 数，也不能只改文字假装设置已生效。

固定版本生成的 `ThreadSettingsUpdateParams` 明确将 effort 用于后续 Turn，`ReasoningEffort` 的 TypeScript 类型为 string。这是本地协议接受值的线索，并非第三方上游兼容性证明。实施前需用固定 Codex 和隔离上游检查实际请求，再对具体网关记录验证来源。HTTP 200 本身也不能证明上游没有忽略参数。

### I04-03：需要“下一轮设置”，不能直接解除禁用

前端 `web/App.tsx:340` 的 `selectionContextDisabled` 同时包含 running，并控制模型、审批、技能、插件、专家。服务端 `server/bridge.ts:1241/1310` 也拒绝有活动任务或授权的会话。隔离浏览器确认三个代表性控件 disabled，直接调用 session/update 同样返回 HTTP 400。

现有 `session_runtime` 是一份已确认配置。修改时会立即执行原生 settings/update；跨网关还会 unload/resume。`run_context` 已经可以保存每次提交的执行快照，但没有独立的下一轮候选状态。解除前端限制会撞上服务端保护；再解除服务端保护可能打断任务或改变审批语义。

推荐保留三层状态：

1. **下一轮设置**：用户最新保存的意图，带修订号，存 SQLite。
2. **已应用设置**：原生线程确认的配置和修订号。
3. **本轮快照**：本次 requestId 固定的模型、权限、扩展和引用，执行中不可被覆盖。

运行中可以保存下一轮设置，选择器显示选中值和小型“下轮生效”状态，可取消待应用更改。当前任务、已有审批仍使用本轮快照。安全应用点建议定义为**下一次原生 turn/start 前的会话级临界区**，而不是 Agent 内部任意一次模型请求。现有原生类型没有为所有扩展提供统一的内部模型调用热切换契约。

此处“下轮”是规划假设：下一次用户提交的 Turn；不自动追加一条空任务，不中断当前 Turn，不新增通用消息队列。模型、审批、持续专家绑定是会话设置；显式技能和插件引用属于下一条消息，用后按 requestId 和修订号消费，不能意外变成永久启用。已经收到成功确认的候选选择应可从 SQLite 恢复，不能只存浏览器内存。未发送的完整正文/附件草稿持久化不因这条需求自动扩展。

失败时保留候选、草稿和原应用状态，明确应用失败，不能悄悄使用旧参数执行。已产生的审批不得因用户选了“完全访问”而被自动批准。服务端重启后重新核对原生线程，保留用户意图，不宣称崩溃前的任务仍在运行。

### I04-04：横向抖动来自滚动条占宽

`web/styles.css:436` 的 `.conversation` 使用 `overflow-y:auto`，未预留滚动条位置；`:496` 的消息列按可用宽度居中。`web/chat-scroll.ts` 的 anchorDisclosure 仅补偿 top 差值。

本轮在 Chromium 显示传统滚动条的环境中，使用真实构建、同一命令详情开关测得：

| 视口 | 折叠 | 展开 | 差异 |
| --- | --- | --- | --- |
| 1366×650 | 消息列 x=429，宽 768 | x=424，宽 768 | 左移 5px |
| 1000×650 | 消息列宽 728 | 宽 718 | 收窄 10px |
| 390×650 | 消息列宽 354 | 宽 344 | 收窄 10px |

同一组测量中 main 和 composer 的水平边界保持不变；主要是聊天滚动容器的内容宽度变化，并非整个浏览器视口变化。见 [展开截图](evidence-issue-04/layout-1366-650-expanded.png)、[折叠截图](evidence-issue-04/layout-1366-650-collapsed.png)。

仅在临时浏览器页面设置 `scrollbar-gutter:stable` 后，再切换详情，消息列 x 和 width 均保持不变。该实验验证修复方向，不代表产品已改动。实施时还应核对消息和输入框的中心对齐，评估 stable 与 stable both-edges 的取舍，而非盲目预留双倍空间。

首次探针沿用 Playwright 默认隐藏滚动条，没有复现；取消 `--hide-scrollbars` 后立即复现。这也解释了已有浏览器测试通过仍会漏掉此问题。新回归必须同时覆盖滚动条占宽和覆盖式滚动条，并跨过“内容刚好需要滚动”的阈值。宽表格、长命令和 iframe 自身溢出是另一条机制，需单独检查，不能都归因于滚动条。

### I04-05：推荐无内边框，保留可见焦点

截图中的矩形不是常态 border。实测 input 的 border 为 0，自动聚焦后 `:focus-visible` 应用了 1px 灰色 outline；来源为 `web/pickers.css:43`，聚焦由 `RuntimeSelector.tsx:259` 主动触发。外层弹层、搜索区分隔线、输入框焦点线形成了三层边界。

建议模型、技能、插件选择器使用统一的无内框搜索行：搜索图标＋文字＋刷新/关闭，保留区域分隔，焦点由整行的细微底色或底线表达，键盘焦点必须可见。聊天搜索采用同一焦点语义，但保留其适合独立对话框的尺寸。不能简单全局 `outline:none`。见 [浅色](evidence-issue-04/search-light.png)、[深色](evidence-issue-04/search-dark.png)。

### I04-06/07：默认选择已有，缺统一语义组件

`ProviderSettings.tsx` 已在卡片点击时提交 makeDefault，当前仍额外渲染 Check。可以去掉勾并保留固定粗细的选中边框；保留 aria-pressed/可访问名称，不把“仅边框”理解为删除非视觉状态。编辑、删除、模型选择已是独立操作，需继续防止冒泡误设默认。尚无默认模型的卡片当前只会聚焦下拉框，不会自动设默认；新设计必须明确要求先选模型，不能显示假成功。

下拉控件当前 `appearance:auto`。padding-right=12px 不等于原生箭头的边距，因此截图中的箭头仍贴近边缘。建议统一一个保留原生 select 行为的包装：控制文字右侧留白，自绘 ChevronDown，距右边约 12–14px，箭头不接收点击；兼顾强制颜色模式。没有必要仅为移动箭头重写完整选项列表。

网关删除按钮与编辑按钮计算颜色完全相同，连接器详情也有同类裸 icon-button；菜单组件却已有 destructive 语义。应把危险操作的视觉语义覆盖到图标按钮和确认入口，而不是每处补一条颜色规则。

图标应按语义区分：编辑现有内容用 Pencil；新聊天可以用 SquarePen；聊天搜索结果宜用 MessageSquare；文件变更可以保留 FilePenLine，它不是“编辑设置”的同义操作。移除未发送附件用 X，不应和永久删除/卸载混成一种危险级别。红色表达破坏性动作，文字/可访问名称继续表达具体对象，颜色不能作为唯一提示。

| 功能/边界 | 共同机制与检查结果 | 状态 | 纳入方式 |
| --- | --- | --- | --- |
| 命令、推理、文件变更、工具结果折叠；流式内容变长 | 同一 conversation 和消息列；跨滚动阈值会改变内容宽度 | 已复现（命令）；其他入口有代码证据 | 修共享容器，补阈值回归 |
