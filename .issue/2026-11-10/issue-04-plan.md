## 目标、不变量与范围

- I04-01：同一会话只有一套对外状态，等待用户必须可辨认、可定位、可恢复。
- I04-02：推理档位名称和交互一致，未知能力不冒充不支持或已支持，选择与实际参数可核对。
- I04-03：执行中的配置固定，用户可保存下一轮选择；已确认保存的候选在 SQLite 中恢复。
- I04-04：展开、收起、流式增量不改变消息列水平基准；主区域、输入框不受连带影响。
- I04-05：搜索减少重复边界，保持键盘可见焦点和明确操作区域。
- I04-06：网关卡片选择即保存默认，边框表达选中，内部按钮和下拉不误触。
- I04-07：同类动作复用图标与危险语义，主题、键盘、触屏行为一致。

不进入本轮：部署架构调整、正式上线验收、通用工作流/消息队列、Agent 内部任意模型请求中途切换、公共插件商店、个人 Codex 配置修改、未发送完整聊天草稿的全量持久化。MCP Apps、文件、私密凭证和原生历史沿用现有能力。

## S1：修共同视觉机制

1. 在实际滚动容器预留稳定滚动条空间，验证消息和输入框的中心基准；保留上下锚点补偿。先复现阈值，再选 stable 或必要的等效布局，不用隐藏滚动条掩盖问题。
2. 检查长命令、JSON、代码、表格、图片、应用与表单的内容收缩/内部溢出边界。展开不能卸载 iframe 或重发工具。
3. 模型/技能/插件的搜索采用一致的无内框搜索行；焦点改由搜索行表达。聊天搜索与扩展搜索遵循同一语义，不全局移除 outline。
4. UI 中“模型网关”统一为“网关”，保留服务端标识。去掉卡片 Check，保持边框厚度不变及可访问选中状态。没有默认模型时先完成模型选择再设默认。
   - 补充反馈：网关名称和模型数量放在同一行；长名称省略，不拉高卡片或挤出编辑/删除，悬停可查看全名。保留用户实际名称，不擅自改名。
5. 统一原生 select 包装：为自绘箭头留固定间距，文字不重叠；保留原生键盘、移动端选择器、禁用状态及强制颜色模式回退。
6. 建立简洁动作映射：编辑 Pencil、新聊天 SquarePen、打开聊天 MessageSquare、删除 Trash2、移除草稿 X；文件变更使用其自身语义。补图标按钮 destructive variant，覆盖网关与连接器详情等漏项，确认/取消和可访问对象名保持完整。

验证：1366/1000/390 宽度，短内容跨滚动阈值和长内容；实际可占宽滚动条及默认覆盖/隐藏滚动条；深浅主题，200% 缩放，键盘焦点、菜单定位、触屏尺寸；失败保存保留旧默认，刷新/重启读回一致。只读网关说明、模型下拉、编辑/删除不可误设默认。

## S2：等待状态归一

1. 等待集合以 source＋requestId 唯一，绑定 threadId、turnId、reason、目标，不保存敏感输入；按多个待处理项聚合摘要。
2. 审批、原生问答、MCP elicitation、真正 `waitForAction` 的 A2UI 使用同一进入/解除/过期/停止路径。单纯展示 App 不算等待。
3. 侧栏在稳定状态区显示“需要批准”/“需要输入”，正文不再同时声称正在执行；点击可定位当前待处理项，新增状态不能抢走输入焦点。
4. 服务重启/原生 offline 后先标记需核对，重新读取权威状态；终态不能被过期等待事件覆盖。时长若继续累计则明确是总历时，不能把等待算作纯模型工作时间。

验证：至少两项并行审批、处理一项仍等待、最后一项解除、A2UI提交/取消/超时、原生输入、MCP授权表单、结束后的迟到事件、切换会话和刷新/重连。独立私密票据不改变无关聊天，也不进入事件正文或追踪内容。

## S3：统一档位与能力判断

1. 固定可理解的中文排序（低/中/高及确有需要的更高档位），将默认/自动和显式值区别存储。保留原生支持的额外值，不任意重映射。
2. 能力记录按网关、模型和版本区分，包含 unknown/supported/unsupported 与证据来源；旧空数组迁移为未知，不能推导为已知不支持。
3. 对能力未知但用户明确选择的档位，设计可验证的尝试路径；对已知不支持的档位禁用并解释。不能强行宣称每个模型都支持全部档位。
4. 统一 gateway/catalog、session/update、thread/start、turn/start 和隐式默认的校验，避免只放开选择器后执行仍被另一入口拦截。
5. 隔离真实 Codex 0.165.0＋模拟上游记录实际请求：支持、拒绝、接受但无法确认是否采用；不把模型自述作为有效证据，不因参数失败自动重复已经可能执行工具的任务。

验证：未知模型显式 low；已知模型不支持值；两个网关同名模型；切换后继承不兼容 effort；默认/恢复/手工目录；原生与上游拒绝。真实第三方的生效证据单列；本轮分析未对 issue 中具体模型作兼容结论。

## S4：候选设置与执行边界

数据方案优先复用现有表和 run_context，增量扩展，不另建 Agent Loop：

- 会话用户意图：desiredRevision、网关、模型、effort、审批、持续专家绑定。普通配置继续存 SQLite，不写 config.toml。
- 已应用配置：appliedRevision 和最后确认的原生设置；明确 pending/applying/failed 状态。
- 下一条消息引用：显式技能/插件的稳定 ID、文档校验信息、选择修订号。与持续专家区分，用 requestId 幂等消费；已确认服务端保存的候选引用可恢复。
- 执行快照：本轮实际 Provider 配置、权限、扩展版本、技能/插件/专家引用，固定到 run_context。UI 同时可查看本轮值与下轮值。

行为顺序：

1. 运行中允许保存候选、编辑下一条输入及其扩展引用；仍阻止同一线程同时执行两轮。断线、权限受限、上传中、保存中的约束分别处理，不共用一个笼统 busy。
2. 会话设置修改采用 CAS，快速多次选择以最后一次确认的版本为准；其他标签页收到更新。撤销候选是新的修订，不是删除执行历史。
3. 下一次 turn/start 前在同一会话锁内冻结配置与引用，校验候选依赖、凭证可用性、权限与版本，然后应用原生设置。跨网关仅在空闲时恢复同一原生 threadId，不重建线程、不重启共享运行时。
4. 应用确认后开始 Turn。失败则保留原应用配置、候选和正文，阻止以错误参数静默发送，支持修正或撤销；不覆盖别的会话。
5. 下一条技能/插件引用只在对应请求实际进入执行后消费；预提交失败可恢复；请求结果未知时先查状态，不重复派发。迟到 ACK 只能清除已提交版本，不能清空后来选择。
6. 原生审批保持原语义。选“完全访问”仅影响未来任务，不能让已存在的审批自动通过；停当前任务不等于取消下轮候选。
7. 重启后保留 SQLite 候选，核对 applied 与原生状态后再使用；共享插件安装/卸载和环境凭证轮换仍受已有空闲约束，不把它们伪装为即时热更新。

验证：A 运行中依次选 B/C，A 实际请求不变，下轮只用 C；同时更改审批与技能；跨网关原线程与历史不变；保存与发送竞争、两个标签页、迟到回包、提交断网、失败重试、切换会话、重启恢复、全局默认变化、候选依赖停用/删除。至少检查上游实际收到参数与原生工具/引用，而非仅看按钮标签。

## 接口、迁移与兼容

- 现有白名单控制接口扩展 desired/applied/pending 和等待摘要；设置保存结果明确区分“已保存待应用”和“已应用”。不开放任意原生 RPC。
- SQLite 在现有 v9 上增量迁移；迁移前备份。旧 session_runtime 作为初始已应用与意图基线，旧记录没有 pending；旧 waiting reason 默认为 unknown 并重新核对。
- 能力三态、状态原因和候选字段对旧会话采用兼容默认；客户端按修订号合并事件与线程读取，避免旧快照冲掉新意图。
- Provider/扩展删除检查增加候选引用；全局默认只影响新会话；当前任务保留所用版本。凭证引用和文件接口继续由服务端校验。
- 不搬迁旧会话目录，不碰个人 `~/.codex` / `~/.agents`，不复制完整原生会话历史到 SQLite。
