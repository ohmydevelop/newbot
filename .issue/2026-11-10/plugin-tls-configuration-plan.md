# 插件配置声明与 TLS 信任：分析和后续计划

本轮用户要求解释 `io.newbot.mcpConfigs`、截图中的 TLS 术语及合理设计；授权范围为调查和规划。本文件不授权修改业务服务器证书、自动信任指纹或修改外部插件。沿用前轮通用插件归属和升级原则，不恢复产品专属适配。

## 目标、问题与不变量

|编号|目标、触发与实际/预期|证据与根因|
|---|---|---|
|PT-01|用户担心 `io.newbot` 又成为外部产品适配。需要明确哪些声明必要、由谁提供|有代码证据：`plugin-descriptor.ts` 按关联表读取同名 MCP 的包内描述；任意插件使用同一实现。它是 newbot v1 宿主发现约定，字段借用 MCPB，不能宣传为完整 MCP/Codex 标准|
|PT-02|填写地址/Token 后查询失败，回答要求配置 CA 或指纹，但页面没有这些字段；预期可从插件详情完成所支持的配置|已复现 TLS 验证失败；当前安装 0.5.1、stdio、configured=true，声明仅 base_url/api_token。插件文档支持 CA_PEM/证书 SHA256，却明确未纳入表单|
|PT-03|使用私有 CA 证书时应能安全传入合法证书文本，不应放宽 URL/请求头的控制字符规则|有代码证据：普通值、模板展开和私密字段都禁止换行；表单只有单行字符串。多行 PEM 不能直接靠新增一个 string 字段接通；文件字段也尚未实现|
|PT-04|MCP 就绪或配置保存不等同业务系统可用；TLS 故障不能被解释成零告警|有代码证据：`plugin/connection/test` 只发现 MCP；截图正确区分失败与无告警，但暴露大量术语且引导到不存在入口。业务错误的宿主结构化恢复目前待验证|

不变量：宿主只解释已声明的数据和能力；配置表单可用性与提示一致；信任绑定到插件/连接器/目标，不能扩散到其他目标；Token 不进入模型/日志；MCP 连接与业务连接状态分别表达；失败不变成空数据成功；配置变更不改变运行中进程的快照。

## 已确认事实与待确认判断

- 当前版本为 CloudWalker 0.5.1，已升级，不继续引用前轮 0.5.0“没有声明”的旧结论。
- `extensions.io.newbot.version=1` 是宿主关联格式版本，`mcpConfigs.cloudwalker` 指向包内描述，并与 `mcp.json` 中连接器 ID 对应。它本身不存 URL/Token。描述提供用户字段及运行参数模板；值保存在 SQLite，敏感值走加密凭证库。
- 当前安装包的 `configuration/cloudwalker.json` 只声明两个字段，实际进程使用 `CLOUDWALKER_BASE_URL` 和 `CLOUDWALKER_API_TOKEN`。普通用户不应手写清单。
- 针对截图地址的只读 OpenSSL 验证握手返回 `self-signed certificate` / verify code 18；没有发送 HTTP 请求或 Token。由此确认当前连接不能通过默认信任验证，但不能据此断言 Token 正确或唯一故障只有证书链。
- 插件文档记载旧式无 SAN 证书联调，但本轮未读取目标证书 SAN/有效期，不能把历史记录替代现状。若 SAN 不匹配，仅导入 CA 仍不足；Go 常规校验使用 SAN，忽略旧 Common Name。
- 本地/公网首页与磁盘一致，引用 `index-DVvWXta9.js`；非旧前端入口导致字段缺失。

## 同类风险范围

|关联入口|共同机制|结果与范围决定|
|---|---|---|
|任意插件的声明发现|宿主不应按产品名猜测字段|有代码证据：通用 io.newbot v1 解析器；保留并明确边界，未来标准适配器归一到同一字段模型，不破坏 v1|
|单行指纹字段|普通 string → 环境模板|有代码证据：现有宿主可承载；插件可声明 64 位 SHA256，插件运行时验证。实际新增包尚未发布/安装，端到端待验证|
|CA/PEM、多行普通值与私密值|共享控制字符验证、大小限制、UI 和运行注入|有代码证据：当前均拒绝换行；只允许在明确声明的证书内容/目标通道中处理合法 PEM，不全局去掉过滤|
|HTTP MCP 与 stdio 插件访问业务 HTTPS|都使用 TLS，但状态所有者不同|有代码证据：本例由插件 Go 进程负责业务 TLS；不把业务 CA 错误设置到 Cloudflare/主 Web 或 Codex 通用 HTTP 连接上|
|MCP 发现、业务鉴权、业务查询|不同阶段容易共用“连接成功”|有代码证据：诊断只做发现；保留无业务调用的默认检查。额外服务检查必须有插件声明的只读操作或专门证书检查，不自动运行任意工具|
|目标更换、证书更新、插件升级|授权和旧值沿用|前轮已验证包/接收方绑定；信任数据的新通道仍待验证，要求目标变化重新确认、错误指纹失败关闭，保留升级旧值供核对|
|多 profile/多插件|信任与凭证的作用域|插件支持 profile，当前表单只 default；不扩大为多实例管理。本轮计划验证一个连接器的信任不会影响其他插件/接收方|
|模型输出错误说明|模型可能给出当前 UI 不存在的恢复建议|已见截图；拟使用工具结构化错误、实际能力和归属生成恢复入口。不得通过匹配任意模型文字赋予配置/执行权限|
|全局系统信任、关闭验证、自动安装 CA|会超出插件边界|不适用本轮方案；不修改系统证书库、不自动接受网络上观察到的指纹|

## 建议设计与实施顺序（尚未实施）

1. **P0：保持声明驱动。** 保留 v1 关联；清单由作者发布。CloudWalker 后续包增加可选指纹字段并绑定既有 `CLOUDWALKER_TLS_CERTIFICATE_SHA256`；这是插件描述扩展，宿主不增加产品名称分支。指纹需由服务管理员通过可信渠道确认，当前网络握手结果不能自动成为信任授权。
2. **P1：补充通用证书输入能力。** 版本化新增字段展示/格式能力，支持受限证书文本或导入证书内容；普通填写继续保存在 SQLite，Token 继续加密。仅在声明允许的 env/可信资源通道处理合法 PEM；HTTP 请求头、URL、命令字段继续拒绝换行；NUL 始终拒绝。CA 证书是信任材料，不是 API Key，不需要服务器私钥。不在环境模板中求值 JSON/任意脚本。
3. **P1：插件补齐信任选项。** 支持系统信任（默认）、自定义 CA 或明确证书指纹，按插件实际能力展示且互斥。业务 TLS 仍由插件校验。CA 模式必须校验目标名称、有效期和用途；插件已有指纹模式以明确证书绑定替代常规 CA/名称校验，并保留有效期/用途约束。显示这种模式的实际语义与证书轮换处理。
4. **P2：统一状态与恢复呈现。** 分开显示已保存/MCP 已就绪/业务连接未验证或失败。针对有结构化故障和明确归属的结果提供“打开插件设置”“查看详情”；主回答用简洁中文，错误码、profile、证书链细节放详情。字段不存在时提示升级插件或不支持，不能引导用户找不存在的设置。无结构化证据时保留错误说明，不猜测具体 TLS 原因。
5. **P3：验证与更新。** 用隔离插件包和本地 TLS 服务测试完整链路，再按已有升级流程安装。新配置于下一轮生效，确保目标 MCP 使用新启动环境，不声称能直接修改已运行子进程的环境。正式证书信任变更另由用户确认具体可信材料。

不处理：改写第三方源码/已安装包、自动升级用户插件、修改真实服务证书、批量发起业务查询、重建线程、全局关闭 TLS、正式部署验收。本轮没有产品实施授权。

## 可观察验收与兼容措施

- 老插件和 v1 描述仍可发现、保存、升级；无需用户编辑 JSON，未知宿主扩展不冒充官方标准。
- 可信系统证书默认成功；未知 CA、自签名、错误 SAN、过期和未生效分别正确失败；导入正确 CA 后仍校验 SAN；指纹错误/轮换不得自动信任。
- 两个插件/目标使用不同 CA/指纹互不影响，TLS 验证失败不发送 Token；脱敏日志和模型结果不出现秘密。
- CA 内容的大小、格式、换行经过完整 UI → SQLite → 运行注入验证；HTTP 头 CRLF/NUL 注入仍被拒绝，不把浏览器本机路径当成服务器文件。
- 保存不执行业务；需要验证的只读操作由用户明确触发。MCP 目录成功不能显示业务连接成功，失败和空结果区分。
- 运行中保存不扰动旧任务；下一轮、撤销、恢复和服务重启读到对应配置。包/接收方变化沿用现有重新确认，保留旧草稿和适用偏好。
- 桌面/手机、键盘、加载/失败/长证书、深浅主题验证；浏览器控制不可用时该项保持未完成。
